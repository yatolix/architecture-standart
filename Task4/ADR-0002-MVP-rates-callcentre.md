### Решение

В файле `MVP_rates_to_callcentre_C4_Context.drawio` можно ознакомиться с контекстной диаграммой системы.

**Пояснения к контекстной диаграмме:**

1. Диаграмма выстроена как дополнение к контекстной диаграмме контекста MVP по депозитам - см. `MVP_deposits_C4_Context.drawio`
2. Зелёным на диаграмме выделены новые взаимодействия необходимые для реализации описанных выше use кейсов.
3. Для реализации требований необходима доработка `системы кол-центра банка`. Во первых в системе должен появиться простой экран со справочной таблицей содержайщей информацию по депозитам. Информация должна быть минимально необходимой: наименование депозита, ставка, базовые условия (частичное снятие, возможность пополнения, автопролонгация, капитализация процентов, минимальная и максимальная суммы открытия, иные условия для открытия - например, если депозит открывается только пенсионерам). Также нужна доработка чтоб `система кол-центра` могла подгружать информацию из `АБС`по`REST API`.
4. В дальнейшем предусмотреть кэширование загруженной информации чтобы она не запрашиваалась каждый раз когда оператор заходит на справочную страницу. Обновлением кэша управлять через `HTTP` заголовки. `АБС` должна давать срок актуальности данных, по истечении которого `система кол-центра` должна запросить апдейт (как правило информация обновляется не чаще чем раз в день).
5. В рамках АБС разработать механизм формирования и отправки файла с информацией по ставкам по `SFTP` в `Систему партнёрского кол-центра.` По умолчанию файл должен формироваться на ежедневной основе, но также предусмотреть возможность отправки файла в срочном режиме в течении дня.

В файле `MVP_rates_to_callcentre_C4_Containers.drawio`содержится диаграмма контейнеров.

**Пояснения к диаграмме контейнеров:**

1. Согласно диаграмме все доработки внутри АБС должны будут производиться в новом сервисе `rates-service` разрабатываемом в рамках MVP по депозитам.
2. Необходимо реализовать REST контроллер для получения информации по депозитам. Так как количество депозитов объективно не может превышать несколько десятков, то в контроллере нет необходимости предусматривать какую-либо фильтрацию или пагинацию. Всегда отдаём всю информацию. В ответе необходимо возвращать заголовок Cache-Control: max-age - со сроком актуальности данных в секундах. Если, к примеру, ставки по депозитам обновляются раз в сутки в полночь, то выставлять в ответе остаточное кол-во секнуд до полуночи.
   В качестве бонуса можно даже рассмотреть вариант переиспользования REST контроллера, который будет разрабатываться для получения информации по депозитам из интернет-банка. По сути это одно и то же.
3. Реализовать в `rate-service` формирование файла в формате `CSV` с информацией по депозитам. По умолчанию файл должен формироваться каждый раз когда ставки пересчитываются. Если процесс пересчёта стартует раз в сутки, то значит файл должен формироваться сразу после пересчёта.
4. После формирования файл сразу отправляется по `SFTP` в `Сиистему партнёрского кол-центра`.
5. Процесс запуска формирования файла сделать асинхронным - он не должен быть жестко привязан к процессу пересчёта ставок, а лишь запускаться из него. Чтобы не усложнять решение в рамках MVP можно создать в БД таблицу для треккинга статуса формирования и отправки файла. Таблица позволит мониторить (не-)успешность формирования и отправки.
6. У файла должно быть фиксированное заранее оговорённое с подрядчиком Системы партнёрского кол-центра имя. Фиксированное имя нужно чтобы каждый раз перезаписывать файл на SFTP сервере провайдера. Нет смысла накапливать там историю файлов, т.к. файлы будут относительно небольшими и операторам всегда требуется только самая актуальная информация. Мы не допускаем ситуации когда оператор сообщает клиенту, как жаль что вы позвонили сегодня, ведь вчера ставка по депозиту была на 2% выше.
7. Так как информация уходит за безопасный контур организации, то нужно предпринять максимальные меры по её защите: сертификаты, шифрование, white листинг IP  и пр.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Можно было бы слать файл со ставками и во внутреннюю систему кол-центра банка чтобы не реализовывать два способа распространения информации. Доработка системы кол-центра тогда бы заключалась не в вызове REST API, а считывании и парсинге CSV файла для отображения на UI. Но кажется, что использование старого протокола SFTP не обосновано в современной системе кол-центра. Лучше сразу делать хорошо. К тому же со временем есть шанс что и внешняя партнёрская система кол-центра сможет перейти на REST.
2. Больше альтернатив на самом деле нет, потому что имея в планах MVP создание сервиса `rates-service` чья зона ответственности - рассчёт актуальных ставок и их централизованное хранение, нет смысла изобретать что-то иное.

**Недостатки, ограничения, риски**

1. Так как сервис `rates-service` будет также использоваться интернет-банком для получения информации, то особое внимание уделить производительности и кешированию. Увеличение запросов из интернет-банка не должно сильно аффектить получение ставок кол-центром.
2. Риск отображение неактульных ставок из-за некорректной реализации кэширования.
3. Риски утечки данных по депозитам через систему партнёрского кол-центра. Риск невысок, т.к.информация в целом публичная и презназначена клиентам. Но могут найтись злоумышленники из операторов кол-центра которые будут сохранять каждый день актуальные ставки, а потом передать их конкурентам. Имея на руках полную информацию по ставкам за достаточно длительный период времени конкурренты могут найти в ней закономерности и раскрыть основные принципы рассчёта ставок. Зная принципы рассчёта, конкурренты смогут построить модель, которая будет предугадывать ставки банка и заведомо предлагать клиентам более выгодные условия. Действовать на опережение по сути.
